## D008 evidence and configuration boundary

`Uedb5ZenMountedStoreContextBuilder` accepts an **optional** `package_entries` list on each separately supplied mount descriptor alongside `container_id`, observed `order`, observed `sequence`, `package_redirects` and `localized_packages`. Each row is `['package_id'=>'FCCBEBA8823DAA3A','file_id'=>111237]` only after validating that the original retained container's `PackageIds`, staged `ue_iostore_packages`, verified `ue_files`, and `ue_uedb5_provider_keys` match. Those example values are from **isolated Satisfactory fixture**; they are not production file IDs for a real Satisfactory game. Later/stronger mounts take the first slot when package IDs overlap; no package coverage or backend authority is fabricated when `package_entries` are omitted. For an **explicitly authoritative** Pass 2 configuration using both mounts and other backends, every mount now needs a `package_entries` field; a labelled `evidence_source` and a list's existence alone still do **not** prove actual completeness.

## D002 compact SQL reason-code storage decision (2026-10-16)

**Decision: do not add `reason_code` to `ue_uedb5_dependency_edges` without a demonstrable SQL-side reason-filtering requirement.** This is an intentionally lossy indexed accelerator: `Uedb5SqlProjectionContract::baselineTables()` declares only outcome, class, package/object identity and resolved provider keys; `PdoUedb5DependencyProjectionPublisher::insertEdges()` deliberately writes that contract. The source-shaped authoritative `.uedb5` `dependency_results` retain `reason_code`; `Uedb5ParityV5ReadService::dependenciesAtIndexes()` supplies detailed rows to `PdoMissingDetailListQuery` and `PdoGameMissingDependencyQuery`, and `CatalogCompactDependencyReadService::compactRows()` now exposes reasons from the V5 file, verified by the D001 SQLite+metadata round-trip. Indexed SQL consumers currently filter/aggregate by outcome rather than distinct reason codes. This closes the *present design question*, **not** independent Epic-cooked fixture acceptance. If a future paginated SQL query must filter by reason at scale, document its measured consumer requirement and add a deliberate schema migration with backfill and tests. No schema change or bulk republish is warranted now.
