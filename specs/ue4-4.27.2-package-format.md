# Unreal Engine 4 Package Format and Reader

## Scope and source authority

This specification documents the package reader represented by the current `ardenee/UnrealEngine4` fork of Epic's Unreal Engine source. The repository identifies itself as Unreal Engine 4.27.2 source code and is a fork of `EpicGames/UnrealEngine`. Its default branch is `release`.

Primary source files reviewed:

- `Engine/Source/Runtime/CoreUObject/Public/UObject/PackageFileSummary.h`
- `Engine/Source/Runtime/CoreUObject/Private/UObject/PackageFileSummary.cpp`
- `Engine/Source/Runtime/CoreUObject/Public/UObject/ObjectResource.h`
- `Engine/Source/Runtime/CoreUObject/Private/UObject/ObjectResource.cpp`
- `Engine/Source/Runtime/CoreUObject/Private/UObject/LinkerLoad.cpp`
- `Engine/Source/Runtime/CoreUObject/Private/UObject/Linker.cpp`
- `Engine/Source/Runtime/Core/Public/Serialization/Archive.h`

The source tree contains compatibility definitions that mention UE5-era package-version enum values. Those conditional branches are part of the source currently in the repository, but UnrealDB must not classify a package as UE5 merely because this source can describe such fields. UE5 remains outside project coverage until an authoritative UE5 source is explicitly supplied.

## Package tag and byte order

`FPackageFileSummary` begins with `Tag`.

The summary accepts `PACKAGE_FILE_TAG` or `PACKAGE_FILE_TAG_SWAPPED`. If the swapped tag is read, the loader normalizes it to `PACKAGE_FILE_TAG` and toggles forced byte swapping on the archive.

Therefore a byte-swapped package is source-supported and must not be rejected solely because its first 32-bit word is the swapped tag.

The summary refuses to begin normal serialization for a loading archive smaller than 32 bytes.

## Legacy version discriminator

Immediately after the tag the modern summary serializes a signed `LegacyFileVersion`.

The examined source defines `CurrentLegacyFileVersion = -9`.

The source documents the negative values as format milestones:

- -2: enum-based custom versions;
- -3: GUID-based custom versions;
- -4: UE3 version removed;
- -5: replacement of the written UE3 compatibility version;
- -6: optimized custom-version serialization;
- -7: texture-allocation summary data removed;
- -8: UE5 version field added;
- -9: early-exit contract for versions too new to parse safely.

When loading, a negative value indicates modern version numbers. A value less than the current understood legacy format causes an early return because subsequent layout cannot be predicted safely.

A nonnegative legacy value is treated as an old UE3 file by this loader and does not proceed as a UE4 package.

## Version fields

For modern summaries, except legacy format -4, a legacy UE3 version integer is consumed.

The source then serializes:

1. `FileVersionUE4`
2. `FileVersionUE5` when `LegacyFileVersion <= -8`
3. `FileVersionLicenseeUE4`

The save path writes legacy UE3 version 864 for a versioned modern package.

The summary's version object is therefore not the old UE3 packed low/high-16-bit `FileVersion` representation.

## Unversioned packages

If UE4, UE5 and licensee version fields are all zero, the source marks the package `bUnversioned`.

In supported runtime configurations the loader substitutes the current engine and licensee versions. In editor configurations where unversioned content is not allowed, summary loading exits before doing so.

An UnrealDB parser must retain the fact that the bytes were unversioned. It must not pretend that a substituted runtime version was serialized in the package.

## Version validation and early exit

The source checks the parsed version before continuing into layout that may differ.

A package below `VER_UE4_OLDEST_LOADABLE_PACKAGE` is too old. A package newer than the running process can also trigger early exit when compatible-version enforcement is active.

This early exit is a format-safety rule: the loader deliberately avoids interpreting later bytes using a layout it does not understand.

UnrealDB must follow the same principle and must not continue with guessed offsets after an unsupported version transition.

## Custom versions

Modern package summaries serialize an `FCustomVersionContainer`.

The custom-version encoding depends on `LegacyFileVersion`:

- -2: enum format;
- -3 through -5: GUID format;
- less than -5: optimized format.

For an unversioned package, the runtime may replace the deserialized empty custom-version container with the current registered custom versions. That replacement is runtime state, not serialized evidence.

Custom versions are part of the package's version contract and cannot be discarded merely because the global UE4 version is recognized.

## Summary layout

After the version/custom-version preamble, the summary serializes fields in source-defined order. The relevant sequence for UE4 packages is:

1. TotalHeaderSize
2. PackageName (historically FolderName; now deprecated/unused)
3. PackageFlags
4. NameCount
5. NameOffset
6. LocalizationId when version permits and editor-only filtering does not remove it
7. GatherableTextDataCount and GatherableTextDataOffset when version permits
8. ExportCount
9. ExportOffset
10. ImportCount
11. ImportOffset
12. DependsOffset
13. SoftPackageReferencesCount and SoftPackageReferencesOffset when version permits
14. SearchableNamesOffset when version permits
15. ThumbnailTableOffset
16. legacy package Guid/SavedHash representation
17. PersistentGuid when applicable and editor-only data is present
18. obsolete OwnerPersistentGuid only in its narrow historical version interval
19. GenerationCount and generation records
20. SavedByEngineVersion or legacy EngineChangelist
21. CompatibleWithEngineVersion when version permits
22. CompressionFlags
23. CompressedChunks array
24. PackageSource
25. AdditionalPackagesToCook legacy array
26. legacy texture-allocation count for legacy summary formats newer than -7
27. AssetRegistryDataOffset
28. BulkDataStartOffset
29. WorldTileInfoDataOffset when version permits
30. ChunkID or ChunkIDs according to version
31. PreloadDependencyCount and PreloadDependencyOffset when version permits

The same source contains later-version conditional fields such as soft-object-path lists, metadata offsets, import type hierarchies, names-referenced count, payload TOC and data resources. They must be parsed only when the serialized package version activates them.

Do not assume a fixed-size summary.

## Package flags

When cooking, the save path adds `PKG_Cooked`.

After loading, transient package flags are cleared. If `PKG_FilterEditorOnly` is present, the archive enables editor-only filtering, which in turn changes whether some summary/import data is serialized or retained.

UnrealDB should preserve the serialized package flags separately from runtime flag cleanup.

## Generations

The summary serializes `GenerationCount`, then that many `FGenerationInfo` records.

The UE4 `FGenerationInfo` structure contains ExportCount and NameCount. Do not import UE3's NetObjectCount into the UE4 generation layout without a version-specific source branch proving it.

## Engine versions

For packages at or after `VER_UE4_ENGINE_VERSION_OBJECT`, `SavedByEngineVersion` is an `FEngineVersion`. Older packages serialize an engine changelist and reconstruct a 4.0.0-style version object on load.

At or after `VER_UE4_PACKAGE_SUMMARY_HAS_COMPATIBLE_ENGINE_VERSION`, `CompatibleWithEngineVersion` is serialized separately; older packages use SavedByEngineVersion as the compatible version.

These fields are metadata about the saving/compatible engine. They are not substitutes for the package serialization version.

## Compression fields

The summary serializes `CompressionFlags` and validates them with `FCompression::VerifyCompressionFlagsValid`.

It then serializes the legacy package-level `CompressedChunks` array.

In this source, if that array is nonempty while loading, the package is rejected: the code states that package-level compression is old and is not loaded by this editor path. The file version is invalidated and summary serialization returns.

Therefore UnrealDB must not assume that a nonempty legacy CompressedChunks array is normal 4.27 package handling merely because earlier UE generations supported it.

Compression used by bulk data, pak files or other containers is a separate format concern.

## Package source and legacy additional packages

`PackageSource` is serialized after the compressed-chunk array.

The source still serializes `AdditionalPackagesToCook` for backward compatibility but explicitly describes it as no longer used.

For legacy summary formats where `LegacyFileVersion > -7`, a texture-allocation count is consumed. The current source expects it to be zero.

## Name map

`FLinkerLoad::SerializeNameMap` seeks to `Summary.NameOffset`.

When `TotalHeaderSize` is available, the loader precaches from NameOffset through the remainder of the header.

It reads exactly `Summary.NameCount` `FNameEntrySerialized` entries and registers their display indices into `NameMap`.

Text archives do not use the binary name table.

UnrealDB must use the source-defined UE4 serialized-name representation; it must not reuse the UE1/UE2 compact-name or UE3 assumptions merely because all are called NameMap.

## Package indices

UE4 wraps object references in `FPackageIndex`, whose stored value is an `int32`.

- index < 0: ImportMap, array index = -index - 1
- index > 0: ExportMap, array index = index - 1
- index == 0: null/root depending on the field's semantics

`FPackageIndex` serializes its raw `int32 Index`.

These are fixed signed integer package indices, not compact indices.

## Import table

`SerializeImportMap` seeks to `Summary.ImportOffset` and reads exactly `Summary.ImportCount` `FObjectImport` records.

The base UE4 import fields serialize in this order:

1. ClassPackage — FName
2. ClassName — FName
3. OuterIndex — FPackageIndex
4. ObjectName — FName

At `VER_UE4_NON_OUTER_PACKAGE_IMPORT` and later, `PackageName` is also serialized.

The current source additionally contains later optional-resource behavior gated by a later package version. That must not be assumed present in an ordinary UE4 package unless its serialized version activates it.

On load, transient import fields are reset:

- SourceLinker = null
- SourceIndex = INDEX_NONE
- XObject = null

The source also contains a cooked/editor-only PackageName save hack: when PackageName is None under editor-only filtering, an existing ObjectName entry can be serialized instead and reset back to None on load. UnrealDB must distinguish this source behavior from genuine package-provider identity.

## Export table

`SerializeExportMap` seeks to `Summary.ExportOffset` and reads exactly `Summary.ExportCount` records.

The source-defined export serialization includes:

1. ClassIndex
2. SuperIndex
3. TemplateIndex when version >= `VER_UE4_TemplateIndex_IN_COOKED_EXPORTS`
4. OuterIndex
5. ObjectName
6. ObjectFlags masked to `RF_Load`
7. SerialSize
8. SerialOffset
9. bForcedExport
10. bNotForClient
11. bNotForServer
12. legacy PackageGuid field while the active version still contains it
13. PackageFlags
14. bNotAlwaysLoadedForEditorGame when version permits
15. bIsAsset when version permits
16. preload-dependency metadata when version >= `VER_UE4_PRELOAD_DEPENDENCIES_IN_COOKED_EXPORTS`

Additional fields in the current source are gated by later version enums and must not be read from an ordinary UE4 package unless activated by its version.

After reading each export, the loader assigns its transient `ThisIndex = FPackageIndex::FromExport(ExportMapIndex)` and computes runtime filtering. Those values are not serialized export fields.

## Export serial size and offset width

Before `VER_UE4_64BIT_EXPORTMAP_SERIALSIZES`, SerialSize and SerialOffset are serialized as signed 32-bit integers and widened in memory.

At and after that version, both are serialized as 64-bit integers.

This version gate is essential. UnrealDB must not impose an arbitrary 32-bit or project-specific payload size limit on later UE4 exports.

## Export payload boundaries

SerialOffset and SerialSize identify an export's serialized object-data region in the linker's underlying archive.

The export table describes those boundaries; object payload interpretation is class/property serialization and is not part of the table itself.

Validation may establish that offsets and sizes are representable and lie within the appropriate package storage, but UnrealDB must not invent smaller maximums not present in source.

## Depends map

UE4 retains a `DependsMap` with one `TArray<FPackageIndex>` per export.

`SerializeDependsMap` seeks to `Summary.DependsOffset`, allocates `Summary.ExportCount` dependency arrays and reads one array per export.

The loader skips it on platforms requiring cooked data and when execution is neither editor nor commandlet. A zero DependsOffset is treated as a badly saved package and skipped by this routine.

The entries use ordinary signed FPackageIndex semantics.

## Preload dependencies

For versions at or after `VER_UE4_PRELOAD_DEPENDENCIES_IN_COOKED_EXPORTS`, the summary can provide `PreloadDependencyCount` and `PreloadDependencyOffset`.

Each export can contain:

- FirstExportDependency
- SerializationBeforeSerializationDependencies
- CreateBeforeSerializationDependencies
- SerializationBeforeCreateDependencies
- CreateBeforeCreateDependencies

`SerializePreloadDependencies` reads the shared dependency list as FPackageIndex values. The five export fields identify contiguous portions of that list used for event-driven/cooked load ordering.

This structure is distinct from the older per-export DependsMap and must not be flattened into it.

## Loader sequence

The examined `ProcessPackageSummary` sequence is materially:

1. SerializePackageFileSummary
2. SerializePackageTrailer
3. SerializeNameMap
4. SerializeSoftObjectPathList when applicable
5. SerializeGatherableTextDataMap
6. SerializeImportMap
7. SerializeExportMap
8. construct text-export readers when applicable
9. FixupImportMap
10. PopulateInstancingContext
11. RelocateReferences
12. ApplyInstancingContext
13. FixupExportMap
14. SerializeMetaData when compiled/applicable
15. SerializeDependsMap
16. CreateExportHash
17. FindExistingExports
18. SerializePreloadDependencies
19. SerializeDataResourceMap when applicable
20. editor-only import hierarchy/dynamic-import processing when applicable
21. FinalizeCreation

This order matters when distinguishing bytes read directly from the package from runtime fixups performed after reading.

## Import fixups are not raw format

`FixupImportMap` applies runtime/editor compatibility behavior including `FCoreRedirects`, class redirects, object redirects, construction of new synthetic import entries, CDO renaming, and clearing old redirected package imports.

These changes occur after the serialized import map has been read.

UnrealDB's raw package metadata must preserve what was actually serialized. If it separately implements source-backed redirect resolution, that must be represented as a derived/resolved view rather than silently rewriting the raw import record.

## Relocation and instancing are runtime transformations

The loader subsequently populates an instancing context, relocates references, applies instancing, and fixes up exports.

Those operations depend on runtime loading context and are not intrinsic bytes in the original package.

They must not be inferred or permanently substituted into raw UnrealDB metadata unless the required context is known and the result is explicitly marked derived.

## Validation behavior

Source-backed structural validation includes at least:

- package is large enough to begin summary parsing;
- magic is normal or swapped;
- legacy summary version is understood;
- package version is within supported loading range before parsing later layout;
- custom-version encoding follows the legacy discriminator;
- compression flags are valid;
- legacy package-level compressed chunks cause rejection in this reader;
- counts and offsets are interpreted according to the exact active version;
- import/export indices use FPackageIndex signed semantics;
- export serial size/offset width follows its version gate.

Arbitrary UnrealDB limits on string length, table count, export size or package size are not format rules unless another authoritative source path proves them.

## UnrealDB conformance requirements

A conforming UE4 reader must:

1. Accept normal and swapped package tags and apply source-equivalent byte order.
2. Parse LegacyFileVersion before assuming the rest of the version layout.
3. Distinguish UE4 package version, licensee version, custom versions and unversioned state.
4. Stop safely on a newer/unknown summary format instead of guessing subsequent offsets.
5. Parse summary fields only when their exact version conditions activate them.
6. Preserve serialized PackageFlags before runtime cleanup semantics.
7. Parse the name table with UE4 FNameEntrySerialized rules.
8. Decode FPackageIndex as a signed fixed int32.
9. Parse imports in source order, including version-gated PackageName.
10. Parse exports in source order with exact version gates.
11. Respect the 32-to-64-bit SerialSize/SerialOffset transition.
12. Treat export payload boundaries as source-provided offsets/sizes without arbitrary project limits.
13. Keep DependsMap and preload dependencies distinct.
14. Keep raw serialized imports separate from CoreRedirect/fixup results.
15. Keep relocation, instancing and filtering marked as runtime-derived behavior.
16. Reject/flag legacy package-level compressed chunks as this reader does rather than routing them through an invented UE4 decompressor.
17. Never borrow UE3/UE2 fallback or layout rules merely because field names resemble them.
18. Do not classify later-version compatibility branches in this source as proof of UE5 project support.

## Revision boundary

This specification is tied to the supplied `ardenee/UnrealEngine4` source tree and its stated 4.27.2 lineage.

Where this source contains compatibility code for package versions introduced later, the conditional behavior is documented only to prevent misparsing. It does not establish UE5 as a supported UnrealDB engine family.

UE4 dependency/provider resolution is intentionally documented separately so its redirect, PackageName, CoreRedirect, outer-chain, cooked and preload-dependency semantics can be reviewed without conflating them with the raw table format.
