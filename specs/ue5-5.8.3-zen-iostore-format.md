# UE5 5.8.3 Zen / IoStore Format

## Scope

This specification documents the cooked UE5 Zen / IoStore structures required by UnrealDB for authoritative package metadata and dependency identity.

Authoritative source:

- root: `L:\Source\Engine\UE5\UE 5.8.3`
- branch/revision policy: UE5 5.8.3 `release` @ `396c9f059903aed5fec78ecd3d437a40c6415368`
- this document covers the file-backed IoStore path (`.utoc` plus `.ucas` partitions) and Zen package headers stored as IoStore package chunks.

This is a different serialization family from classic LinkerLoad `.uasset` / `.umap` packages. Zen identity must not be flattened into classic `FObjectImport` / `FPackageIndex` semantics.

## Core invariant

For file-backed Zen packages, dependency identity is split between two authoritative sources:

1. the package's Zen header provides typed `FPackageObjectIndex` values and ordered imported public-export hashes;
2. the containing IoStore package-store entry provides the ordered imported package IDs.

A PackageImport can only be resolved losslessly when both pieces of context are available.

## `.utoc` table of contents

### Header

`FIoStoreTocHeader` begins the `.utoc` file. UE5 5.8.3 uses the 16-byte magic:

`-==--==--==--==-`

The current source accepts `EIoStoreTocVersion` from `DirectoryIndex` through `Latest`:

| Value | Version |
|---:|---|
| 2 | `DirectoryIndex` |
| 3 | `PartitionSize` |
| 4 | `PerfectHash` |
| 5 | `PerfectHashWithOverflow` |
| 6 | `OnDemandMetaData` |
| 7 | `RemovedOnDemandMetaData` |
| 8 | `ReplaceIoChunkHashWithIoHash` / `Latest` |

Versions older than `DirectoryIndex` and newer than `Latest` are rejected by the UE5 5.8.3 reader.

The header stores, in its fixed source layout:

- magic and TOC version;
- `TocHeaderSize`;
- TOC entry count;
- compression-block entry count and entry size;
- compression-method name count and fixed name length;
- logical compression block size;
- directory-index size;
- partition count and partition size;
- `ContainerId`;
- encryption-key GUID;
- `EIoContainerFlags`;
- perfect-hash seed/overflow counts;
- reserved fields.

UE5 validates `TocHeaderSize == sizeof(FIoStoreTocHeader)` and `TocCompressedBlockEntrySize == sizeof(FIoStoreTocCompressedBlockEntry)`. In the audited UE5 5.8.3 Win64 layout, `FIoStoreTocHeader` is 144 bytes and `ContainerId` begins at byte offset 56; there is no extra padding between `PartitionCount` and `ContainerId`. UnrealDB must reject a mismatching layout rather than continuing with guessed offsets.

`EIoContainerFlags` values are source-defined:

- `Compressed = 1 << 0`;
- `Encrypted = 1 << 1`;
- `Signed = 1 << 2`;
- `Indexed = 1 << 3`;
- `OnDemand = 1 << 4`.

### TOC array order

After the header, UE5 reads the TOC arrays in this order:

1. `TocEntryCount` `FIoChunkId` records;
2. `TocEntryCount` `FIoOffsetAndLength` records;
3. version-gated perfect-hash seed data and overflow indices;
4. `TocCompressedBlockEntryCount` compression-block records;
5. the fixed-width compression-method name block;
6. signing data when the container is signed;
7. directory-index bytes when requested and the container is indexed;
8. per-chunk metadata.

The TOC parser must derive offsets from this source order. It must not scan for chunk IDs or compression records heuristically.

### Chunk IDs and packed offsets

`FIoChunkId` is exactly 12 bytes. Byte 11 is `EIoChunkType`. Relevant source values include:

- `ExportBundleData = 1` — package data / Zen header + export payload;
- `BulkData = 2`;
- `OptionalBulkData = 3`;
- `MemoryMappedBulkData = 4`;
- `ScriptObjects = 5`;
- `ContainerHeader = 6`;
- `PackageStoreEntry = 10`.

`CreatePackageDataChunkId(PackageId)` constructs an `ExportBundleData` chunk whose first eight bytes contain the raw `FPackageId` value, chunk index zero, and chunk type 1. `CreateContainerHeaderChunkId(ContainerId)` uses the same rule with `ContainerHeader` type 6.

`FIoOffsetAndLength` is exactly 10 bytes: five bytes of offset followed by five bytes of length. Each quantity is stored most-significant byte first. This is not a native `uint64` pair.

`FIoStoreTocCompressedBlockEntry` is exactly 12 bytes:

- 40-bit physical offset;
- 24-bit compressed size;
- 24-bit uncompressed size;
- 8-bit compression-method index.

The source getter treats the offset and size fields as the packed little-endian bit layout in `Data[12]`; UnrealDB must reproduce those source getters exactly rather than treating the entry as three normal integers.

Compression method index zero means `NAME_None` / no compression. The serialized method-name block contains only the explicit non-None methods; UE5 prepends `NAME_None` in memory. UE5 5.8.3 writes compression method names in 32-byte slots.

## `.ucas` partitions and chunk reconstruction

IoStore logical chunk offset/length is independent from physical `.ucas` block placement.

For a requested chunk:

- first block = `logical_offset / CompressionBlockSize`;
- last block is calculated from the aligned logical end;
- a compression block's physical offset selects the partition using `physical_offset / PartitionSize`;
- the file offset within that partition is `physical_offset % PartitionSize`.

Partition zero is `<base>.ucas`. Further partitions are `<base>_s1.ucas`, `<base>_s2.ucas`, and so on.

UE5 reads each block using its compressed size rounded up to the 16-byte AES block size. If `Encrypted` is set, the aligned bytes are AES-decrypted before decompression. It then dispatches the compression method named by the block entry. Method zero is copied directly; other methods go through the engine compression dispatcher.

UnrealDB must not report a compressed/encrypted package chunk as invalid merely because the local process lacks the required codec/key. That is an `unresolved/unsupported ingestion capability` boundary until the exact required decoder/key is available.

Oodle is a normal UE5 IoStore compression possibility. The supplied UE5 source contains Oodle SDK headers, but the current DEV source checkout does not contain an `oo2core*_win64.dll`. Therefore a PHP staging reader may support Oodle through an explicitly configured compatible decoder, but must not pretend Oodle blocks were verified when no decoder is available.

## IoStore container package-store header

The container header is itself an IoStore `ContainerHeader` chunk. Its payload uses `FIoContainerHeader` serialization and begins with:

- signature `0x496f436e`;
- `EIoContainerHeaderVersion` as a 32-bit enum;
- `ContainerId`;
- `PackageIds`;
- serialized file package-store entries;
- optional-segment package IDs and store entries;
- redirect name map;
- localized-package records;
- package redirects;
- version-gated soft-package-reference data.

UE5 5.8.3 defines container-header versions:

| Value | Version |
|---:|---|
| 0 | `Initial` |
| 1 | `LocalizedPackages` |
| 2 | `OptionalSegmentPackages` |
| 3 | `NoExportInfo` |
| 4 | `SoftPackageReferences` |
| 5 | `SoftPackageReferencesOffset` / `Latest` |

The current loader rejects versions earlier than `NoExportInfo` (3). UnrealDB's UE5 5.8.3 policy must follow that supported range rather than silently accepting older layouts.

### File package-store entries

`FFilePackageStoreEntry` contains two `TFilePackageStoreEntryCArrayView` records:

1. ordered `ImportedPackages` (`FPackageId` values);
2. shader-map hashes.

Each C-array view is two `uint32` fields: `ArrayNum` and `OffsetToDataFromThis`. The offset is relative to the address of that specific 8-byte view header.

`CreateContainerHeader()` writes all fixed `FFilePackageStoreEntry` records first and their array payloads afterward. The source calculates the relative offset from the current view header to the corresponding appended data. A file package-store entry is therefore 16 bytes before its pointed-to data.

For dependency identity, UnrealDB must preserve the ordered imported package IDs exactly. Reordering, sorting, or deduplicating them would corrupt `FPackageObjectIndex` PackageImport meaning.

The source sorts packages by global `FPackageId` when constructing the header, so each `PackageIds[n]` corresponds to fixed store entry `n`.

### Optional segments

The header separately stores `OptionalSegmentPackageIds` and `OptionalSegmentStoreEntries`.

For a manual optional segment, its store entry's imported-package view contains `OptionalSegmentImportedPackageIds`. Auto-optional packages can instead appear in the ordinary package-ID/store-entry list of the optional container. These distinctions are source state and must not be collapsed into ordinary hard dependencies.

### Localized packages, redirects, and soft references

Localized-package entries serialize:

- source `FPackageId`;
- source package `FMappedName` using the container name map.

Package redirects serialize:

- source `FPackageId`;
- target `FPackageId`;
- source package `FMappedName`.

These mappings must be retained as container provenance. They are not equivalent to object redirectors in a package export map.

Soft package references use a container-wide deduplicated, sorted `FPackageId` list plus one relative C-array view per package. Each view points to `uint32` indices into the deduplicated package-ID list. Thus the soft-reference list for package `n` is reconstructed through the package-aligned view `n`; it is not an unordered container-global dependency list.

At container-header version 4 the soft-reference object is inline. At version 5 it is located through `FIoContainerHeaderSerialInfo` (`int64 Offset`, `int64 Size`). The loader validates that the declared serialized range fits in the chunk.

## Zen package chunk identity

An ordinary Zen package data chunk is `EIoChunkType::ExportBundleData` with the raw package ID in the first eight chunk-ID bytes. The package's raw `FPackageId` is therefore available from container/package-store identity and must be preserved as unsigned 64-bit data.

UEDB5 canonical storage must use fixed-width binary or 16-hex-digit representation for `FPackageId`, `PublicExportHash`, and raw `FPackageObjectIndex::TypeAndId`. PHP signed integer conversion is not lossless for these values.

## `FPackageObjectIndex`

`FPackageObjectIndex` serializes one raw `uint64 TypeAndId`:

- low 62 bits = value/id;
- top two bits = type;
- type 0 = Export;
- type 1 = ScriptImport;
- type 2 = PackageImport;
- type 3 = Null; all-one bits are the default null/invalid value.

For PackageImport, the low 62-bit payload is constructed as:

`(ImportedPackageIndex << 32) | ImportedPublicExportHashIndex`

Decoding therefore yields:

- imported-package index from bits 32..61;
- imported-public-export-hash index from bits 0..31.

The authoritative cross-package key is then:

`ImportedPackageIds[ImportedPackageIndex] + ImportedPublicExportHashes[ImportedPublicExportHashIndex]`

A package name or derived object path may assist display/search, but it cannot replace this key.

ScriptImport stores the source-generated 62-bit import hash. UE5 generates object-path script hashes after lowercasing and converting `.` / `:` separators to `/`, then masks off the top two type bits. UnrealDB should retain the serialized hash; it must not require successfully reversing that hash to a path.

## Zen package header

`FZenPackageSummary` is a fixed source structure at the start of the package chunk:

1. `uint32 bHasVersioningInfo`;
2. `uint32 HeaderSize`;
3. `FMappedName Name` (raw index/type word + number);
4. `uint32 PackageFlags`;
5. `uint32 _Unused` (formerly cooked-header size);
6. `int32 ImportedPublicExportHashesOffset`;
7. `int32 ImportMapOffset`;
8. `int32 ExportMapOffset`;
9. `int32 ExportBundleEntriesOffset`;
10. `int32 DependencyBundleHeadersOffset`;
11. `int32 DependencyBundleEntriesOffset`;
12. `int32 ImportedPackageNamesOffset`.

`HeaderSize` bounds the complete Zen header. All table offsets are relative to the start of the package chunk and must be monotonic/range-valid before any table view is created.

### Versioning preamble

If `bHasVersioningInfo != 0`, immediately after the fixed summary UE5 serializes `FZenPackageVersioningInfo`:

- `EZenPackageVersion` (`uint32`);
- `FPackageFileVersion` as UE4 `int32` then UE5 `int32`;
- licensee version `int32`;
- complete custom-version container.

`EZenPackageVersion` values in this source are `Initial`, `DataResourceTable`, `ImportedPackageNames`, and `ExportDependencies` (latest).

After optional versioning, packages at `VERSE_CELLS` or later (and packages with no embedded versioning info, following the source's current-package assumption) serialize `FZenPackageCellOffsets`: cell-import-map offset then cell-export-map offset. Older versioned packages make both offsets equal `ExportBundleEntriesOffset` and therefore have no cell maps in this layout.

### Package name map

The package `FNameMap` follows the versioning/cell preamble and is loaded as `FMappedName::EType::Package`.

The name batch binary format is:

1. `uint32 NumNames`;
2. if nonzero, `uint32 NumStringBytes`;
3. `uint64 HashVersion`;
4. `NumNames` saved `uint64` hashes;
5. `NumNames` two-byte `FSerializedNameHeader` records;
6. `NumStringBytes` string bytes.

A name header uses bit 7 of its first byte as the UTF-16 flag; the remaining 15 bits store the character length. The separated string payload contains exactly that length in ANSI bytes or UTF-16 code units and does not carry a terminator per entry.

`FMappedName` itself serializes two `uint32` values: an index/type word and number. Its index uses 30 low bits and the top two bits identify Package, Container, or Global name-map type. UEDB5 must retain the raw index/type word and number as well as resolved display text when available.

### Bulk-data map preamble

At `EUnrealEngineObjectUE5Version::DATA_RESOURCES` or later (and when no embedded versioning info is present), the source consumes a bulk-data-map preamble after the package name map:

- `uint64 BulkDataPad` — number of pad bytes to skip;
- exactly that many pad bytes;
- `int64 BulkDataMapSize`;
- `BulkDataMapSize / sizeof(FBulkDataMapEntry)` fixed entries.

Each `FBulkDataMapEntry` retains serial offset, duplicate serial offset, serial size, flags, cooked index, and padding. These records describe payload ownership/location and must remain distinct from UObject exports.

## Zen header table slicing

After the source-shaped preamble, `FZenPackageHeader::MakeView()` derives table counts from adjacent offsets:

- `ImportedPublicExportHashes`: `uint64` values from `ImportedPublicExportHashesOffset` to `ImportMapOffset`;
- `ImportMap`: `FPackageObjectIndex` values from `ImportMapOffset` to `ExportMapOffset`;
- `ExportMap`: `FExportMapEntry` values from `ExportMapOffset` to `CellImportMapOffset`;
- `CellImportMap`: `FPackageObjectIndex` values from `CellImportMapOffset` to `CellExportMapOffset`;
- `CellExportMap`: `FCellExportMapEntry` values from `CellExportMapOffset` to `ExportBundleEntriesOffset`;
- export-bundle entries from `ExportBundleEntriesOffset` to `DependencyBundleHeadersOffset`;
- dependency-bundle headers from `DependencyBundleHeadersOffset` to `DependencyBundleEntriesOffset`;
- dependency-bundle entries from `DependencyBundleEntriesOffset` to `ImportedPackageNamesOffset`;
- imported-package-name data from `ImportedPackageNamesOffset` to `HeaderSize`.

Every byte span must be non-negative, wholly inside `HeaderSize`, and an exact multiple of the relevant fixed record size. UnrealDB must reject malformed spans before indexing into them.

The source additionally requires the export-bundle entry count to equal:

`(ExportMap.Num + CellExportMap.Num) * 2`

because each export has one Create command and one Serialize command.

## Zen export map

`FExportMapEntry` serializes in this exact order:

1. `uint64 CookedSerialOffset`;
2. `uint64 CookedSerialSize`;
3. `FMappedName ObjectName`;
4. raw `FPackageObjectIndex OuterIndex`;
5. raw `FPackageObjectIndex ClassIndex`;
6. raw `FPackageObjectIndex SuperIndex`;
7. raw `FPackageObjectIndex TemplateIndex`;
8. `uint64 PublicExportHash`;
9. object flags serialized through `uint32`;
10. export filter flags serialized through `uint8`;
11. three padding bytes.

The package payload for an export begins at `HeaderSize + CookedSerialOffset`. `CookedSerialSize` is the source-defined payload length.

`PublicExportHash` is the authoritative cross-package public-export identity supplied to PackageImport lookup. It must be retained verbatim and not replaced by a recomputed hash.

### Cell maps

A Zen cell import is a raw `FPackageObjectIndex` and retains its typed 64-bit identity.

`FCellExportMapEntry` serializes:

- `uint64 CookedSerialOffset`;
- `uint64 CookedSerialLayoutSize`;
- `uint64 CookedSerialSize`;
- `FMappedName CppClassInfo`;
- `uint64 PublicExportHash`.

Cell exports are a distinct source table. They must not be silently appended to the ordinary UObject export map merely to make a common index space.

## Export and dependency bundles

`FExportBundleEntry` is two `uint32` values:

- local export index;
- command type (`Create = 0`, `Serialize = 1`).

`FDependencyBundleHeader` contains:

- `int32 FirstEntryIndex`;
- a 2x2 `uint32 EntryCount` matrix describing dependencies from Create/Serialize to Create/Serialize.

`FDependencyBundleEntry` contains one serialized local `FPackageIndex`. This is a load-order dependency reference local to the Zen package's import/export indexing context; it is not the same representation as the cross-package `FPackageObjectIndex` import map.

UEDB5 must therefore preserve dependency-bundle edges separately from ordinary object/package dependency results. An edge can affect load ordering without introducing a new provider package identity.

## Imported package names

When the Zen version supplies imported package names, the tail section is `FZenPackageImportedPackageNamesContainer`:

- one serialized name batch;
- one `int32` FName number for every loaded name entry.

Epic only materializes this array in editor builds in `FZenPackageHeader::MakeView`, but the serialized bytes remain source metadata. UnrealDB may parse them for inspection/display; they do not replace ordered imported `FPackageId` identity from the package-store entry.

## Script imports

A `ScriptImport` is not a package import. Its raw 62-bit hash resolves against the runtime script-object table (`FScriptObjectEntry` / loader global import store), whose entries themselves carry mapped object name and raw global/outer/CDO-class `FPackageObjectIndex` values.

Where UnrealDB has authoritative script-object container data, it may retain and resolve that table. Where it does not, the ScriptImport must remain a lossless hash identity with `unresolved` provenance rather than being fabricated as an ordinary package dependency.

## Required UEDB5 package-family representation

Zen/IoStore UEDB5 snapshots use a distinct package family such as `zen-iostore`, with an explicit UE5 5.8.3 source-policy identifier.

At minimum a fully verified file-backed package snapshot must preserve or durably reference:

- source `.utoc` container identity/version/flags and matching `.ucas` partition provenance;
- raw package `FPackageId` and chunk ID;
- the exact package-store entry and ordered imported package IDs used for this package;
- applicable optional-segment imported package IDs;
- package redirects, localization mapping, and soft-reference provenance relevant to the package;
- Zen summary/versioning/custom versions and package name map;
- imported public-export hashes;
- raw import map, typed/decoded without discarding `TypeAndId`;
- export map including all raw graph indices and public hashes;
- cell maps;
- export bundle entries;
- dependency bundle headers/entries;
- bulk-data/data-resource map where present;
- imported package names where serialized;
- explicit ingestion capability/provenance for compression and encryption.

## Dependency classification

The Zen reader must keep these source classes separate:

- hard PackageImport / public-export-hash reference;
- ScriptImport;
- optional-segment package import;
- container soft package reference;
- cell/Verse import;
- dependency-bundle load-order edge;
- redirect/localization mapping;
- runtime-derived or otherwise non-deterministically-resolvable reference.

Those classes feed the UEDB5 five-state dependency outcome contract (`resolved`, `package_only`, `common`, `missing`, `unresolved`). Optional/soft/runtime-derived meaning belongs in classification/provenance; it must not create extra persisted status values.

## Verification requirements

A Zen package cannot be declared fully verified merely because its package header parses. Verification requires all source context needed by its references.

For every file-backed package UnrealDB must validate:

1. the `.utoc` magic, supported version, header sizes and array bounds;
2. chunk-ID / offset-length count parity;
3. compression-block indices and method indices used by the package chunk;
4. required `.ucas` partition existence and block bounds;
5. successful decryption/decompression when the chunk requires them;
6. the package chunk ID maps to the expected raw `FPackageId`;
7. the container header is readable and its `ContainerId` matches provenance;
8. the package ID has exactly one corresponding store entry in the selected container context;
9. all store-entry relative array views are in bounds;
10. the Zen `HeaderSize` and every table span are in bounds/aligned to its source record size;
11. mapped names refer to the correct name-map type and valid name index;
12. every PackageImport index is in range for both ordered imported-package IDs and imported-public-export hashes;
13. every local Export-type object index is in export-map range where the source uses it;
14. public-export hashes and other unsigned-64 identities are preserved byte-for-byte;
15. export bundle count is exactly two entries per ordinary/cell export;
16. dependency bundle header/entry ranges are valid;
17. UEDB5 round-trip preserves the complete source-shaped identity above.

If a required codec or encryption key is unavailable, structural TOC/container metadata may still be inspected, but the affected package must not be promoted to fully verified Zen UEDB5 metadata.

## Current UnrealDB boundary

This specification is the source contract for Step 2 of the UEDB5 work. The existing production runtime remains UEDB4 and classic UE5 UEDB5 staging remains isolated.

Step 2 implementation may add isolated IoStore/Zen staging readers and UEDB5 snapshot builders. It must not:

- teach the production UEDB4 reader to understand Zen;
- register production files as V5;
- publish V5 SQL projections;
- introduce a V5/V4 runtime fallback;
- begin catalogue-wide migration.

Those operations belong to later UEDB5 migration/cutover steps.

## Conformance rule

Where this document conflicts with generic IoStore knowledge, older UE5 layouts, third-party tooling, or historical UnrealDB assumptions, the cited UE5 5.8.3 source controls. Unsupported source branches must be reported explicitly rather than approximated from a related engine version.
