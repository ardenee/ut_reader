## Provider linker selection

`VerifyImportInner()` establishes a source linker in three source-backed ways:

- a null-outer `Package` import loads its `ObjectName` package;
- an import with effective `PackageName` loads that explicit package;
- a serialized NAME_None is retained as raw FName evidence but is not HasPackageName() and therefore does not select a provider named None;
- otherwise a child import whose outer is an import inherits the outer import's source linker.

An import whose outer is an export is legal only when `PackageName` supplies the source package.
The static resolver takes one already-selected physical provider linker per package.
It deliberately rejects duplicate selections for the same package instead of combining
exports from multiple files into a synthetic provider that Epic could never load.

When a caller has several same-name physical files, provider selection is a separate
catalog concern. Each candidate must be tested as a complete physical linker.

## Root package imports

A null-outer import must have `ClassName == Package`. Any other null-outer import is
an inappropriate outermost import in Epic's loader and is classified invalid.

A valid package import establishes `SourceLinker` but not an export `SourceIndex`.
The UEDB5 resolver therefore reports `package_only` rather than inventing an export.

## ExportHash candidate order

`CreateExportHash()` walks exports from low to high index and prepends each export to
its hash bucket. `VerifyImportInner()` consequently walks matching same-name exports
from higher export index to lower export index.

The UEDB5 resolver preserves this ordering. Once the first name/outer candidate is a
forbidden private export, it does not search a later public duplicate.

## Initial candidate match

A provider export first needs the same `ObjectName`.
There is one class-based discriminator at this stage: an `ObjectRedirector` export is
only a direct candidate when the import itself requests `ObjectRedirector`. An ordinary
import skips a redirector and the outer `VerifyImport()` wrapper may retry as a redirector.
Following its destination requires runtime object/payload state, so UnrealDB reports that
case as `runtime_only` rather than pretending the redirector is the requested object.

## Outer qualification

When the consumer import outer is another import, Epic qualifies the candidate export
against the already-resolved outer:

- if the outer has a source linker but no source export index, it is the top-level package;
  the candidate export must have null `OuterIndex`;
- if child and outer share the same physical source linker, the candidate `OuterIndex`
  must equal the outer's resolved export package index;
- if child and outer use different source linkers, the candidate outer must itself be an
  import in the child's provider linker, and that provider import's `ObjectName` must equal
  the consumer outer import's `ObjectName`.

In the cross-linker case, differing outer class package/name does not reject the candidate.
Epic records that outer import for stronger verification when its class object is created.
The UEDB5 result records `deferred_outer_class_verification=true`.

When the consumer outer is an export, this import-side outer qualification block is not
run; explicit `PackageName` already supplied the source linker.
## Class identity is deferred, not a lookup key

After name/redirector/outer/private checks succeed, Epic compares the requested class
package/name with `GetExportClassPackage()` / `GetExportClassName()`.

A mismatch does **not** reject the provider export and does not cause the hash walk to
continue. `VerifyImportInner()` sets `SourceIndex` and adds the import to
`ImportsToVerifyOnCreate` for later verification with a real class object.

UnrealDB therefore records `deferred_class_verification=true` while retaining the match.
This is intentionally different from UE3 exact-tuple import verification.

## UE5 public flag

UE5 5.8.3 defines:

`RF_Public = 0x00000001`

`0x00000004` is `RF_MarkAsNative`, not `RF_Public`.

Section 4 records UE5 classic object flags using canonical 16-hex-digit UEDB5 storage
while declaring their source serialization width as 32 bits. The resolver tests the UE5
`RF_Public` bit from that canonical value and does not reuse UE3 or legacy flag constants.

## Private-export graph exceptions

A private candidate export is allowed when any one of Epic's three consumer-linker graph
predicates is true:
- `ImportIsInAnyExport(ImportIndex)`;
- `AnyExportIsInImport(ImportIndex)`;
- `AnyExportShareOuterWithImport(ImportIndex)`.

The implementation reproduces the `FLinkerTables` traversal itself rather than replacing
these checks with a generic path-prefix test. In particular, `ResourceIsIn()` advances
through the package-index graph in the exact source-defined order.

If none applies, the deterministic file-backed resolver rejects the private export.
Editor `SafeReplace` behavior is runtime/editor state and is not treated as resolution.

## Optional imports

`bImportOptional` remains part of source identity. When the selected optional package or
object is absent, UnrealDB reports `optional_missing` instead of the hard `missing` class.

This distinction is required so optional resources do not inflate hard missing-dependency
counts during the later UEDB5 projection/cutover work.

## Runtime-only boundaries

The classic loader has additional paths that cannot be reproduced from package metadata
alone. Section 5 does not fabricate results for:

- CoreRedirect/config-driven package or object remapping;
- instancing-context package remapping;
- native/transient or memory-only UObject lookup;
- editor placeholder/safe-replace behavior;
- runtime-created dynamic imports;
- redirector destination loading;
- IoStore/Zen package-store resolution.

Missing `/Script/...` providers are therefore classified `runtime_only` by this static
resolver rather than being converted into a fake disk-package dependency.

Dynamic imports remain outside the serialized ImportMap and Section 5 never creates
synthetic import rows for them.

## Production boundary

Section 5 is intentionally not connected to `PdoDependencyResolver` or the production
`CompactDependencyRebuilder`. Those services still consume UEDB4 metadata, which cannot
represent the UE5 fields required by this resolver losslessly.

Production wiring must wait until the UEDB5 migration/publication section has:

1. reparsed authoritative UE5 bytes into UEDB5;
2. selected one physical provider linker for each package requirement;
3. published the required compact SQL lookup/provenance data;
4. switched dependency rebuilding to the UEDB5 source rows.

Until then, this class is an offline/staging source-parity verifier.

## Verification contract

`verify-uedb5-ue5-classic-dependency-resolution.php` proves:
- top-level package/source-linker establishment;
- same-linker outer matching;
- explicit `PackageName` selecting a different linker;
- cross-linker provider-import outer matching and deferred outer-class verification;
- import-with-export-outer behavior;
- class mismatch deferral;
- ObjectRedirector separation;
- `RF_Public` bit `0x1` rather than `0x4`;
- all three private-export graph exceptions;
- ExportHash traversal order and first-private-match behavior;
- optional missing classification;
- rejection of synthetic multi-provider linker composition;
- runtime-only script-package handling.

Zen/IoStore dependency resolution is explicitly outside this specification.
