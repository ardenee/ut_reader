This document is the implementation audit for UnrealDB's static UE4 import dependency resolver. It is intentionally stricter than a feature summary: a behavior is not called source-aligned unless the source branch is either implemented exactly or explicitly classified as unavailable to a static catalogue.

## Status vocabulary

- **implemented** — static UnrealDB behavior matches the reviewed source rule.
- **gap** — deterministic source behavior is reconstructible but current code does not match it.
- **metadata-unresolved** — source behavior is deterministic, but current UEDB4 did not retain required serialized information.
- **payload-unresolved** — source behavior requires serialized UObject payload state not retained by UEDB4 table metadata.
- **runtime/config-only** — behavior depends on live UObject state, load flags, instancing, platform/build state or CoreRedirect configuration; UnrealDB must not invent it.
- **catalogue policy** — UnrealDB behavior needed only because the catalogue can contain duplicate physical providers; not an Epic loader rule.

## Explicitly non-static branches

These source paths are real, but a static arbitrary-package catalogue does not possess the state required to replay them safely:

- `FixupImportMap` CoreRedirect class/object/value remapping and newly injected package Imports;
- instancing-context package remapping;
- existing/fully-loaded UObject package state;
- native transient object and native CDO lookup;
- `LOAD_FindIfFail` / `ANY_PACKAGE` lookup;
- memory-only package lookup;
- `WITH_IOSTORE_IN_EDITOR` `StaticFindAllImportObjects` live-object resolution;
- dynamic export/class state not serialized in the classic `FObjectExport` table.

Project policy remains: do not emulate CoreRedirect/config remapping without the exact originating redirect data. Preserve the serialized requirement instead.

## UnrealDB provider-selection boundary

Epic resolves one package through the engine package resource/load system. UnrealDB may have several physical files with the same logical package name. Choosing among those files is therefore **catalogue policy**, not UE4 source behavior.

Current policy may score candidates by exact per-Import matches, but:

- one logical package resolves through one physical provider;
- matches from multiple provider files are never combined;
- a failed sibling Import does not erase successful siblings from the chosen provider.

This policy must be described as catalogue behavior, not as an Epic `VerifyImport` rule.

## Corrections to the older UE4 dependency spec

The previous `ue4-4.27.2-dependency-resolution.md` incorrectly stated that `VerifyImportInner` calls `IsPackageReferenceAllowed`. No `IsPackageReferenceAllowed` symbol exists in the authoritative 4.27.2 source tree, and no such call exists in `VerifyImportInner`. That statement must be removed.

The older spec also documented ObjectRedirector discrimination during the initial export match but did not document the wrapper's second-pass ObjectRedirector retry and destination validation. The wrapper behavior is part of the authoritative import-verification flow and must be documented explicitly.

## Required next implementation checkpoints

Do not run another broad UE4 dependency repair until the remaining deterministic gaps have been handled and separately contracted.

Completed after this audit: **imported-class package identity** now follows the exact immediate-outer `GetExportClassPackage` rule, with regressions for both Import and Export immediate outers.

Remaining checkpoints:

1. **ObjectRedirector fallback** — detect the second-pass redirector candidate exactly. With current UEDB4 table metadata, classify a matching redirector as redirect-target/payload unresolved unless an authoritative destination can be recovered; do not resolve the original import to the redirector export itself.
2. **Cross-linker outer branch** — determine which cases are statically reconstructible from retained metadata. Anything dependent on redirect destination, PackageName omitted by UEDB4, instancing, or live loader state remains explicitly unresolved.
3. Re-run the residual provider-present audit only after these contracts pass.

Until those checkpoints are complete, UE4 dependency resolution should be described as **partially source-aligned with known audited gaps**, not fully source-aligned.

## Mechanical branch-completeness pass

A conditional-by-conditional pass over `LinkerLoad.cpp` covering `VerifyImport` and `VerifyImportInner` (including the local `LoadImportPackage` lambda and `WITH_IOSTORE_IN_EDITOR` helper) gives the following additional dispositions:

- `FPlatformProperties::HasEditorOnlyData()` changes redirect failure fatality, not static provider identity — **runtime/error policy**.
- invalid export-hash indices are linker corruption/error handling, not a fallback provider rule — **malformed-provider failure**.
- `PKG_Compiling`, fully-loaded package state, serialize-context state and `bIsGatheringDependencies` change live loading behavior — **runtime-only**.
- `WITH_IOSTORE_IN_EDITOR` cooked-package `StaticFindAllImportObjects` uses live UObjects — **runtime-only**.
- private-export `SafeReplace` warning behavior never assigns a successful `SourceIndex` on that branch — **no additional static success rule**.
- in-memory/package-instance package resolution and top-level package `XObject` recovery are **runtime/config-only**.
- `LOAD_FindIfFail`, native/transient lookup and the moved-native-`UScriptStruct` fallback depend on loaded class/object state — **runtime-only**.
- final serialize-context attachment changes loader bookkeeping only — **no static provider effect**.

The separate Event-Driven Loader import path is in `Serialization/AsyncLoading.cpp`, not `VerifyImportInner`. `FAsyncPackage::SetupImports_Event()` / `FindExportFromImport()` use active async package/linker state and an `ObjectNameWithOuterToExport` table. That path is therefore **runtime/async-only** and must not be presented as a deterministic `VerifyImportInner` fallback.
