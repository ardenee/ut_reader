This document is the implementation audit for UnrealDB's static UE4 import dependency resolver. It is intentionally stricter than a feature summary: a behavior is not called source-aligned unless the source branch is either implemented exactly or explicitly classified as unavailable to a static catalogue.

## Status vocabulary

- **implemented** — static UnrealDB behavior matches the reviewed source rule.
- **gap** — deterministic source behavior is reconstructible but current code does not match it.
- **metadata-unresolved** — source behavior is deterministic, but current UEDB4 did not retain required serialized information.
- **payload-unresolved** — source behavior requires serialized UObject payload state not retained by UEDB4 table metadata.
- **runtime/config-only** — behavior depends on live UObject state, load flags, instancing, platform/build state or CoreRedirect configuration; UnrealDB must not invent it.
- **catalogue policy** — UnrealDB behavior needed only because the catalogue can contain duplicate physical providers; not an Epic loader rule.

## `VerifyImports` / `VerifyImport` wrapper

| Source behavior | Static classification | Current UnrealDB state |
|---|---|---|
| `VerifyImports` invokes `VerifyImport(ImportIndex)` independently for each serialized Import | reconstructible | **implemented** — successful sibling imports are retained; one failed sibling no longer invalidates the provider |
| `VerifyImport` first calls `VerifyImportInner` using the serialized class identity | reconstructible | **implemented** |
| When the package/linker was found but the requested export was not, retry the same object as `/Script/CoreUObject.ObjectRedirector` | reconstructible detection | **implemented** -- redirector candidates are detected separately and never returned as the original resolved target |
| If the ObjectRedirector export exists, create/preload it and read `DestinationObject` | requires UObject export payload | **payload-unresolved** in UEDB4; `CatalogAssetMetadataService` already labels redirectors `object_redirector_unparsed` |
| Redirect destination is valid if it is a CDO, otherwise its class or a superclass name matches the original Import.ClassName | requires loaded destination/class hierarchy | **payload/runtime-unresolved**; must not treat the redirector export itself as the resolved original import |
| When an outer Import resolves through ObjectRedirector, `VerifyImport` rewrites that outer `SourceLinker`/`SourceIndex` from `DestinationObject` before descendant `VerifyImportInner` continues | requires redirector payload destination | **implemented classification** — descendants under a table-detected redirector outer are `payload_unresolved`, never guessed as missing/resolved |
| Failed redirect restoration, warning/fatal policy and `IsSuppressableBlueprintImportError` | loader/UI behavior | **runtime-only**, no dependency-provider effect to emulate |

## Explicitly non-static branches

These source paths are real, but a static arbitrary-package catalogue does not possess the state required to replay them safely:

- `FixupImportMap` CoreRedirect class/object/value remapping and newly injected package Imports;
- instancing-context package remapping;
- existing/fully-loaded UObject package state;
- native transient object and native CDO lookup;
- `LOAD_FindIfFail` / `ANY_PACKAGE` lookup;
- memory-only package lookup;
- `WITH_IOSTORE_IN_EDITOR` `StaticFindAllImportObjects` live-object resolution;
- dynamic export/class state not serialized in the classic `FObjectExport` table.

Project policy remains: do not emulate CoreRedirect/config remapping without the exact originating redirect data. Preserve the serialized requirement instead.

## Residual provider-rejection reason audit

`catalog/bin/audit-ue4-missing-verifyimport.php` is a read-only residual audit. It must use the same deterministic table-level resolver as production and must not introduce alternate success rules.

For provider-present groups that still fail `VerifyImport`, the audit explains each failed required Import/provider attempt with the first source-shaped rejection boundary reached by the static resolver:

- `object_name_not_found` — no provider export has the serialized `Import.ObjectName`;
- `class_name_mismatch` — the object name exists, but not with the serialized `Import.ClassName`;
- `class_package_mismatch` — ObjectName/ClassName candidates exist, but fail the full-ClassPackage-first / short-ClassPackage fallback rule;
- `outer_mismatch` — object/class/class-package candidates exist, but none has the SourceIndex-derived outer required by `VerifyImportInner`;
- `private_export_rejected` — the matching export lacks `RF_Public` and none of the exact UE4 editor graph exceptions applies;
- `outer_import_unresolved` — the serialized outer Import did not resolve first, so the child cannot be validated;
- `object_redirector_target_unavailable` / `object_redirector_ancestor_target_unavailable` — the source-defined redirector path requires `DestinationObject` payload state;
- `v4_package_context_unavailable` — the serialized graph requires package context that UEDB4 did not retain.

The audit reports both failed Import/provider-pair counts and residual package-group counts. These are diagnostic counts only. A rejection reason must never be promoted to a static match unless a reviewed Epic source branch supplies the missing success condition.

`unexpected_unmatched_candidate`, `unclassified`, and graph-integrity reasons are invariant/diagnostic failures to investigate, not fallback matching rules.

## UnrealDB provider-selection boundary

Epic resolves one package through the engine package resource/load system. UnrealDB may have several physical files with the same logical package name. Choosing among those files is therefore **catalogue policy**, not UE4 source behavior.

Current policy may score candidates by exact per-Import matches, but:

- one logical package resolves through one physical provider;
- matches from multiple provider files are never combined;
- a failed sibling Import does not erase successful siblings from the chosen provider.

This policy must be described as catalogue behavior, not as an Epic `VerifyImport` rule.

## Corrections to the older UE4 dependency spec

The previous `ue4-4.27.2-dependency-resolution.md` incorrectly stated that `VerifyImportInner` calls `IsPackageReferenceAllowed`. No `IsPackageReferenceAllowed` symbol exists in the authoritative 4.27.2 source tree, and no such call exists in `VerifyImportInner`. That statement must be removed.

The older spec also documented ObjectRedirector discrimination during the initial export match but did not document the wrapper's second-pass ObjectRedirector retry and destination validation. The wrapper behavior is part of the authoritative import-verification flow and must be documented explicitly.

## Audit completion status

The deterministic file-backed UE4 4.27.2 `VerifyImport` / `VerifyImportInner` branches that can be reconstructed from current UEDB4 metadata are now either implemented or explicitly classified.

Completed after this audit:

- **Imported-class package identity** follows the exact immediate-outer `GetExportClassPackage` rule.
- **ObjectRedirector second-pass detection** reports a valid redirector candidate separately; the original Import remains payload-unresolved because UEDB4 does not retain/parse `DestinationObject`.
- **ObjectRedirector outer propagation** follows the source control flow: if a serialized outer Import reaches the redirector second pass, descendant Imports remain payload-unresolved until `DestinationObject` can provide the rewritten source linker/index.
- **Cross-linker / PackageName boundary** is classified rather than guessed: the different-linker outer check is deterministic only once the child's actual SourceLinker is known. Serialized `PackageName` can establish that at v520+, but current UEDB4 drops the field; pre-520 different-linker cases require runtime redirect/instancing state.

For existing UEDB4 v520+ snapshots, exact Import-outer explicit-PackageName reconstruction requires reparsing the original package or migrating to metadata that retains PackageName. Export-outer v520+ cases remain the structurally provable subset that v4 can mark metadata-unresolved without guessing.

The next step is residual-data diagnosis/reclassification, not another un-audited resolver rule.

For current UEDB4 metadata, UE4 dependency resolution should be described as **source-aligned for the reconstructible static branches, with explicit metadata/payload/runtime unresolved boundaries**. Do not describe UEDB4 as capable of replaying discarded PackageName or redirector DestinationObject state.

## Mechanical branch-completeness pass

A conditional-by-conditional pass over `LinkerLoad.cpp` covering `VerifyImport` and `VerifyImportInner` (including the local `LoadImportPackage` lambda and `WITH_IOSTORE_IN_EDITOR` helper) gives the following additional dispositions:

- `FPlatformProperties::HasEditorOnlyData()` changes redirect failure fatality, not static provider identity — **runtime/error policy**.
- invalid export-hash indices are linker corruption/error handling, not a fallback provider rule — **malformed-provider failure**.
- `PKG_Compiling`, fully-loaded package state, serialize-context state and `bIsGatheringDependencies` change live loading behavior — **runtime-only**.
- `WITH_IOSTORE_IN_EDITOR` cooked-package `StaticFindAllImportObjects` uses live UObjects — **runtime-only**.
- private-export `SafeReplace` warning behavior never assigns a successful `SourceIndex` on that branch — **no additional static success rule**.
- in-memory/package-instance package resolution and top-level package `XObject` recovery are **runtime/config-only**.
- `LOAD_FindIfFail`, native/transient lookup and the moved-native-`UScriptStruct` fallback depend on loaded class/object state — **runtime-only**.
- final serialize-context attachment changes loader bookkeeping only — **no static provider effect**.

The separate Event-Driven Loader import path is in `Serialization/AsyncLoading.cpp`, not `VerifyImportInner`. `FAsyncPackage::SetupImports_Event()` / `FindExportFromImport()` use active async package/linker state and an `ObjectNameWithOuterToExport` table. That path is therefore **runtime/async-only** and must not be presented as a deterministic `VerifyImportInner` fallback.
