# Unreal Engine 4 Dependency and Import Resolution

## Scope

This specification documents dependency and import resolution behavior proven by the supplied `ardenee/UnrealEngine4` source tree, identified as Unreal Engine 4.27.2 lineage.

It complements `ue4-4.27.2-package-format.md`. That document describes serialized tables. This document describes how the engine interprets those tables to identify package dependencies and resolve imported objects.

## Serialized dependency evidence

An `FObjectImport` supplies the core dependency evidence:

- ClassPackage
- ClassName
- OuterIndex
- ObjectName
- PackageName when the active package version serializes it

The import's transient resolution state — XObject, SourceLinker and SourceIndex — is not serialized.

A package catalogue must therefore derive dependencies from the serialized import graph first. Runtime resolution results are a separate layer.

## FPackageIndex semantics

All import/export relationships use signed `FPackageIndex` values:

- negative = import; array index is `-Index - 1`;
- positive = export; array index is `Index - 1`;
- zero = null.

Outer traversal may cross imports and exports. UE4 source explicitly contains cases where an import has an export outer and vice versa. A dependency implementation that assumes every import outer chain contains imports only is incorrect.

## Import path construction

`FLinkerTables::GetImportPathName` begins at the import and repeatedly follows `OuterIndex` until null.

Each resource's `ObjectName` is prepended.

Ordinary nested resources are separated with `.`.

A subobject delimiter is used at the package/object boundary when the current resource is not a package and its outer is null or has class Package.

Therefore object identity is not merely `ObjectName`; the outer chain is part of the path.

`GetImportFullName` prepends `ClassName` plus a space to the path name.

## Outermost resource

`ResourceGetOutermost` follows `OuterIndex` until it reaches a resource whose OuterIndex is null.

This is the authoritative graph operation for identifying the outermost serialized resource when no explicit PackageName overrides package selection.

Do not infer the provider solely from the first or last textual name without traversing the package-index graph.

## Explicit PackageName

Newer UE4 imports can serialize `PackageName`.

`VerifyImportInner` treats an import as a package-loading boundary when either:

- it has PackageName, or
- its OuterIndex is null.

For loading, the package name is:

- `Import.GetPackageName()` when PackageName is present;
- otherwise `Import.ObjectName` for the top-level package import.

This is a major difference from older engines: a non-root import can explicitly identify its provider package.

Consequently UnrealDB provider selection must prefer a genuinely serialized PackageName where the UE4 version contains it, rather than always deriving the provider from the outermost import.

## PackageName editor/cooked caveat

The serializer contains a filtering optimization in which, while saving filtered editor-only data, a None PackageName can be represented using ObjectName and reset to None on load when PackageName equals ObjectName.

That engine-side normalization depends on archive filtering state.

UnrealDB must not blindly treat every equal PackageName/ObjectName pair as an independently asserted provider without considering the applicable serialization/filtering contract.

## Package imports

An import whose OuterIndex is null is required by `VerifyImportInner` to have ClassName == Package. A null-outer import with a non-Package class is reported as an inappropriate outermost import.

A null-outer Package import causes the engine to load/find that package.

For static dependency extraction, this makes top-level Package imports direct package requirements unless the package represents runtime-only/native state that cannot be mapped to a catalogue file.

## Imports with explicit provider packages

For a non-root import with PackageName, the engine loads the named package before resolving its object.

The import may even have an export outer; source explicitly permits that case provided PackageName is set.

Therefore:

`required package = explicit PackageName`

takes precedence over the older assumption:

`required package = topmost import ObjectName`.

## Recursive outer verification

When an import's OuterIndex points to another import, `VerifyImportInner` recursively verifies that outer first.

The child normally inherits the outer import's SourceLinker if the child has not already acquired another source linker.

This means object resolution is hierarchical: the outer's resolved package/export context constrains the child's candidate export.

UnrealDB should likewise resolve outer chains before claiming an exact imported-object match.

## Export matching

Once a SourceLinker is available, the engine hashes by `Import.ObjectName` and searches the source package's export hash chain.

A candidate first needs the same ObjectName.

There is also special ObjectRedirector discrimination: unless the import explicitly requests ObjectRedirector, an ObjectRedirector export is not accepted by this initial match.

Name equality alone is not sufficient.

## Outer matching

For a candidate source export, the source validates the outer relationship.

If the imported outer has a SourceLinker but no SourceIndex, it represents the top-level package case; the candidate export must have a null OuterIndex.

If import and outer use the same source linker and the outer has a resolved SourceIndex, the candidate export's OuterIndex must equal `FPackageIndex::FromExport(OuterImport.SourceIndex)`.

If import and outer use different source linkers, the candidate export outer is expected to be an import in the source linker. Its ObjectName is compared with the requested outer's ObjectName. If class/package identity differs, the source defers stronger class verification until object creation.

Thus exact dependency verification is path/outer aware, not a global object-name lookup.

## Dynamic/external-package imports

Editor-only source supports dynamic imports used when objects move into external packages.

When the ordinary outer linker does not directly provide the child import, the loader can examine dynamically added imports, inspect their source linkers, find exports with matching ObjectName, and walk the import/export outer chains in parallel.

A dynamic candidate is accepted only when both outer chains terminate together after matching ObjectName at each level.

This is runtime/editor machinery. It is not evidence that an arbitrary UnrealDB package with a matching object name is a valid provider.

Without the dynamic-import context serialized or reconstructible from the catalogue, UnrealDB must not invent this fallback.

## Class identity

After a matching export is found, the source compares:

- Import.ClassName versus source export class name;
- Import.ClassPackage versus source export class package.

A mismatch does not immediately select some other arbitrary export. The import is marked for additional verification when it is created and an actual class object is available.

For catalogue-level exact matching, class package + class name are therefore meaningful constraints and should be retained.

Do not reduce UE4 object requirements to object path alone when class identity is available.

## Public/private export requirement

A matched source export is normally required to have `RF_Public`.

The source has explicit exceptions for imports/exports that are intertwined through outer relationships:

- the import is inside any export;
- any export is inside the import;
- an export with an import outer shares the same outermost resource.

Outside those cases, a private source export is not a normal valid cross-package import.

UnrealDB should therefore distinguish an object merely present in a candidate package from an object valid for external import.

## Package privacy

After loading a provider package, `VerifyImportInner` calls `IsPackageReferenceAllowed`.

An illegal reference to a private package is rejected by runtime loading.

The exact allowability can depend on package/runtime context. Where UnrealDB cannot reconstruct that context, it must not turn a mere filename match into a source-equivalent verified dependency.

## Native and in-memory-only resolution

If no source export is found, the loader can resolve certain objects already in memory, including native transient objects, class default objects of native transient classes, and objects in in-memory-only packages.

It can also use `LOAD_FindIfFail` to search by name.

These paths depend on live UObject state and load flags. They are not reconstructible from standalone package bytes.

UnrealDB must label such cases unresolved/runtime-only rather than fabricating a package provider.

## Script packages

When an import requires a script package and the engine cannot find it, the package is recorded in the CoreRedirect known-missing package set and a missing script-package warning is emitted.

Script/native package handling is therefore not equivalent to proving that a disk package with a similar short name is required.

## CoreRedirects

UE4's loader applies `FCoreRedirects` during import fixup and verification.

The source supports redirects for package, class and object identities, value/subobject changes, instance-only redirects and known-missing entries.

These redirects are runtime/configuration data, not all derivable from a package's bytes.

The older `ActiveClassRedirects` configuration path is explicitly described in source as deprecated and translated into FCoreRedirect entries.

For UnrealDB's static catalogue:

- preserve the raw serialized import;
- do not silently replace it with a redirected name;
- only produce a redirected/resolved identity if the exact redirect data used for that game/runtime is known;
- do not create generic redirect guesses.

## Important UnrealDB constraint on redirects

A source-backed redirect mechanism is not permission to implement configuration-dependent remapping without the configuration.

The engine reads redirect configuration from runtime config and registered CoreRedirect data. UnrealDB processing arbitrary UE files does not inherently possess the originating game's active redirect configuration.

Therefore a dependency cannot be declared resolved through a redirect merely because UE4 has a redirect system.

This follows the same project rule used for earlier engine families: runtime/config-only fallback behavior is documented but not emulated without its required inputs.

## Instancing and package remapping

Before loading an import package, the engine calls `InstancingContext.RemapPackage`.

It may load package A's data into package B's in-memory instance and propagate the instancing context.

This is runtime load context, not serialized provider identity.

UnrealDB should record the serialized package requirement, not a hypothetical PIE/instanced package name.

## Dependency tables versus imported objects

UE4 contains two additional dependency structures:

### DependsMap

There is one array of FPackageIndex values per export.

It represents serialized object dependencies associated with exports.

### PreloadDependencies

Newer cooked/export formats can contain a shared preload dependency list plus per-export ranges divided into:

- serialization-before-serialization;
- create-before-serialization;
- serialization-before-create;
- create-before-create.

These encode load ordering among package indices.

Neither structure replaces the ImportMap as the source of external imported-object identity.

A package may therefore have:

- package/object requirements derived from imports;
- object dependency edges from DependsMap;
- load-order edges from preload dependencies.

UnrealDB should preserve those meanings separately.

## Required package identification

For each serialized import, the source-backed static rule is:

1. If the import has a genuine serialized PackageName, that is its explicit provider package requirement.
2. Otherwise traverse OuterIndex.
3. If the outer chain reaches a null-outer Package import, that package import's ObjectName is the provider package identity.
4. If the chain crosses an export, retain the mixed import/export path; do not collapse it using an import-only assumption.
5. If no provider can be established from serialized data, mark it unresolved rather than applying an invented fallback.

Duplicate imports may of course map to the same required package.

## Required object identification

A required object's serialized identity consists of, as applicable:

- provider package;
- complete outer/object path;
- ObjectName;
- ClassPackage;
- ClassName.

The engine verifies outer structure against the provider export map and checks class identity after finding the candidate.

Therefore a provider package containing an export with the same leaf name is insufficient proof by itself.

## Provider selection in a catalogue

The engine normally asks its package resource system for a package by package name. UnrealDB instead has a catalogue containing potentially many files/profiles/versions with equivalent package names.

The official source does not define how UnrealDB should choose among those catalogue duplicates.

Therefore provider selection among multiple catalogue files is an UnrealDB policy layer, not an engine-format rule.

It may use game/profile scope and exact package identity, but it must not claim that arbitrary heuristics such as newest file, largest file, nearest filename, or first database row are UE4 behavior.

After choosing candidate package files, object verification should use the source-backed path/class/public rules above.

## No source-backed arbitrary fallback

No reviewed UE4 path establishes a general fallback of:

- same leaf object name anywhere;
- same filename stem anywhere;
- same class name while ignoring package;
- nearest package name;
- cross-game/profile search;
- case-normalized fuzzy object matching;
- accepting a private export merely because it exists.

Such behavior must not be added as UE4 dependency resolution unless another authoritative source path explicitly proves it.

## Case semantics

The relevant source comparisons use FName identity for ObjectName, ClassName and ClassPackage.

UnrealDB should implement UE4 FName semantics consistently rather than inventing an independent filesystem-style case rule for object identity.

Package-file discovery can have platform/resource-manager concerns distinct from FName object matching; do not conflate the two.

## Raw versus resolved metadata

UnrealDB should maintain a clear distinction:

### Raw

What the package serialized:

- ClassPackage
- ClassName
- ObjectName
- OuterIndex
- PackageName
- dependency package indices

### Derived from the package graph

- import path
- outermost resource
- static required package
- static required object path

### Runtime-derived

- SourceLinker
- SourceIndex
- XObject
- CoreRedirect results
- instanced package names
- memory-only/native object matches
- dynamic external-package imports
- LOAD_FindIfFail results

Only the first two groups can be reproduced from arbitrary package bytes without additional runtime/configuration state.

## Failure interpretation

Failure to statically identify a catalogue provider is not proof that the original UE4 runtime could never load the import.

The runtime has native objects, mounted package resources, redirects, dynamic imports, instancing, already-loaded objects and load flags unavailable to a static catalogue.

Conversely, finding a same-named object in some catalogue file is not proof that the runtime would accept it.

UnrealDB should report these states distinctly rather than converting uncertainty into either a false success or false corruption verdict.

## UnrealDB conformance requirements

A conforming UE4 dependency implementation must:

1. Decode all OuterIndex values as FPackageIndex.
2. Support mixed import/export outer chains.
3. Use serialized PackageName as the provider when present and valid for the package version.
4. Otherwise derive the provider by traversing to the null-outer Package import.
5. Construct object paths from the full outer chain.
6. Resolve/verify outer imports before child imports.
7. Require candidate export ObjectName equality.
8. Verify candidate outer relationships, not merely leaf names.
9. Retain ClassPackage and ClassName and use them for exact verification where possible.
10. Respect RF_Public for ordinary cross-package object imports and document source-defined structural exceptions.
11. Keep package requirements, DependsMap edges and preload-order dependencies separate.
12. Preserve raw imports before any redirect/fixup representation.
13. Never apply CoreRedirects without the actual applicable redirect data.
14. Never emulate instancing, dynamic-import or memory-only fallbacks from guesses.
15. Never treat catalogue duplicate-provider selection policy as an official UE4 format rule.
16. Mark dependencies that require unavailable runtime/config state as unresolved/runtime-only.
17. Do not borrow UE1/UE2/UE3 fallback rules unless the UE4 source independently implements them.
18. Do not use UE5-only compatibility branches as evidence for UE4 behavior unless the serialized UE4 version activates the branch.

## Revision boundary

This document is tied to the supplied `ardenee/UnrealEngine4` source and its stated 4.27.2 lineage.

The repository currently contains compatibility code that references later package-version concepts. Those branches do not authorize UnrealDB to infer UE5 behavior. UE5 remains outside scope until authoritative UE5 source is supplied.

Most importantly, this specification deliberately does not turn UE4's extensive runtime resolution machinery into static catalogue heuristics. Where the engine requires runtime package mounts, configuration redirects, instancing state, native objects or dynamic imports, UnrealDB cannot reproduce that result from package bytes alone.
